## Findings

1. **Should fix, P2 — stale startup tasks clear replacement ownership.** `Sources/Application/AppEngine.swift:87–101`, with recovery at lines 116–123. Recovery cancels and clears the current task, then immediately launches another. Cancellation is cooperative: when the old invocation eventually returns, its unconditional `defer` clears the new task's handle. A continuation-controlled executable probe reproduced this while the replacement remained suspended. Subsequent recovery can no longer cancel the replacement, and another `advance()` can start duplicate work. The generic error path also lacks the cancellation/current-invocation check. Give each startup invocation an identity and allow only the current invocation to clear ownership or publish completion/error, or wait for cancellation to finish before replacing it. Add a recovery regression covering old-task success and failure.

2. **Should fix, P2 — cancellation retains the observation's captured resources.** `Sources/Application/Observation+onChange.swift:37–43` and `Sources/Application/ObservationToken.swift:23–25`. The installed closure strongly captures the token, value reader, and callback. `cancel()` changes only a Boolean; it cannot release those closures. A probe cancelled and discarded a token, discarded the callback's owner, and found the weak owner still alive while the observed source remained alive and unchanged. Dropping an uncancelled token also leaves the token alive. This undermines the documented ownership model and differs from NotificationToken teardown. Store the callback/value closures in token-owned state, let the installed observer capture the token weakly, and clear the closures on cancellation. Define dropping-token behavior explicitly and update the sample's discarded-token call if lifetime becomes retention-based. Add weak-reference release tests.

3. **Should fix — complete the standards cleanup in changed files.** Strict swift-format lint fails in Package.swift, AppEngine.swift, AppState.swift, NotificationCentre+onChange.swift, NotificationToken.swift, UserDefaults+onChange.swift, ApplicationTests.swift, and TestApplicationApp.swift. `git diff --check` finds five newly introduced trailing-whitespace lines. Documentation is missing for the new token's stored state, notification-token stored state/deinitializer, and the observable test fixture's value; broader missing documentation remains in changed AppEngine and sample/test files. TestApplicationApp.swift retains its nonstandard header, multiple primary types, and non-final helper classes; AppEngine.swift also contains two separate default view types. Run formatting and complete the applicable file/documentation checklists. Several findings predate this PR, but the required checklist applies to every changed file.

4. **Suggestion — synchronize observation tests with actual callbacks.** `Tests/ApplicationTests/ChangeMonitoringTests.swift:31–42,59–65`. The tests assume one Task.yield completes delivery; confirmations are incremented by the test body after the expectation. Confirm from the callback and await a callback completion signal. All 20 repeated runs passed, so this is a determinism weakness, not a reproduced failure.

## Codebase Effect

### Made Obsolete

No stale references to deleted guideline paths or the removed onChangeSendable API remain in this repository. The replacement main-actor onChange helper is used by the sample and tests. External users of onChangeSendable will need migration as part of release planning.

### Simplification Now Possible

ObservationToken uses ObservationIgnored despite having no Observable macro; this annotation appears unnecessary. The sample ServiceB installs an additional withObservationTracking callback whose task does nothing. These can be simplified separately.

Checked: read both token implementations, the full observation helper, sample TestServices.swift, and the removed helper implementation. Compared task and observer ownership before and after the change.

### Duplication

No new duplicated observation implementation was found in the package. The two token types represent different underlying cancellation mechanisms, so a shared abstraction is not yet justified.

Checked: searched for onChange, onNotification, ObservationToken, NotificationToken, withObservationTracking, startupTask, and AppEngine call sites. Read Bookish's AppEngine conformance, startupTask initialization, and its startup-loop test. That test only checks entry into starting and presence of a handle; it does not cover recovery races.

### Design Clarity

Explicit startup ownership and cancellable observation are useful boundaries, but the two ownership defects must be fixed to make the contracts reliable. The observation documentation should state that synchronous mutations can coalesce before the main-actor callback runs; it currently promises a callback for each subsequent change. Duplicate-start prevention also asserts before its guard, so repeated advance calls abort debug builds; clarify whether this is a caller precondition or an idempotent operation.
